# tally plan

## Goal
Decide, with measurements, whether the CLI (`src/cli.js`) should parse bank exports with the vendored `vendor/rowstream` library. Adopt it only if on a ~2 GB export it (a) peaks under 200 MB RSS and (b) parses multi-line quoted memos correctly. If it passes, switch the CLI over; if not, say why and what the alternatives are. Done = a go/no-go note backed by numbers, plus (on go) a CLI that streams the file and sums amounts correctly.

## Baseline
2026-11-14 · tests: 1 pass, 0 fail (`npm test`, node 22.23) · lint: none configured · build: none
Today's CLI reads the whole file with `readFileSync` and splits on `\n`: wrong for quoted newlines, and a 2 GB file exceeds Node's max string length, so it can't work at that size anyway.

## Now
Stage 1 of 4 · Spike: rowstream
Risk: UI only (throwaway harness, nothing shipped; synthetic data only, never a real export)
Checks:
- [ ] A synthetic ~2 GB CSV exists with a known row count and known amount total, containing multi-line memos, `""` escapes, CRLF rows and commas inside quotes (proof: run a generator script, its printed ground truth)
- [ ] Peak RSS of rowstream streaming that file is measured and reported against the 200 MB bar (proof: run `/usr/bin/time -v`, not a test: it's a 2 GB run)
- [ ] rowstream's row count and amount total equal the ground truth and an independent parser (Python `csv`) on the same file (proof: run and diff)
- [ ] Targeted edge cases pass or fail on small fixtures: `""` split across the 64 KB chunk boundary, `\r\n` split across it, multi-byte char across it, quoted field ending at EOF with no trailing newline, unterminated quote, BOM, blank lines (proof: a small script, each case reported)
- [ ] Findings are in `docs/research/rowstream-spike.md` with a GO / NO-GO / GO-AFTER-PATCH verdict (proof: the note)
Open: none

## Stages
- [ ] 1. Spike: rowstream — measure memory and correctness on a 2 GB synthetic file and edge-case fixtures
- [ ] 2. Gate — act on the verdict (no-go: stop and record; patch needed: fix `vendor/rowstream` and re-run stage 1's checks)
- [ ] 3. Switch the CLI — stream rows, accumulate the total without building an array, tests first
- [ ] 4. End-to-end proof — run the real CLI on the 2 GB file under the memory bar

## Decisions
- 2026-11-14 · This is a spike-first plan; nothing in `src/` or `vendor/` changes until stage 1 gives a verdict — the user asked to plan before writing, and adoption is conditional on the measurements.
- 2026-11-14 · Memory bar = peak RSS < 200 MB (`/usr/bin/time -v`, "Maximum resident set size"), also run once with `node --max-old-space-size=64` to show memory doesn't grow with file size — RSS is what actually hits the machine; the 64 MB run catches hidden accumulation.
- 2026-11-14 · Fixture is synthetic, generated by a script kept in the scratchpad (outside the repo) and written outside the repo, deleted after — no real bank data, and 2 GB doesn't belong in git. Needs ~2 GB free disk; check with `df` first.
- 2026-11-14 · Correctness is judged against two oracles: the generator's ground truth and Python's `csv` module on the same file — a parser can't grade itself.
- 2026-11-14 · Reading rowstream's source already suggests three things to test, not conclusions: (1) `""` split across a chunk boundary sees `chunk[i+1] === undefined`, so the escaped quote is likely dropped silently; (2) an unterminated quote accumulates the rest of the file into one string (unbounded memory); (3) `src/tally.js` `total(rows)` takes an array, so the CLI must accumulate while streaming or the memory win is lost.
- 2026-11-14 · Column layout assumed as the CLI has it today: amount in column index 1, header on row 1, amounts as decimal strings. Revisit only if a real export's layout differs (open question below).
- 2026-11-14 · Agents: balanced (default). The work is small and sequential; stage 1 can use one agent for the generator and Python oracle in parallel with the edge-case script.
- 2026-11-14 · No external research: nothing outside the repo changes this plan; the evidence comes from running the code.
- 2026-11-14 · Scale check: not plan-sized for `jbit:fix` (new behaviour, money parsing) and not large enough to chart (4 stages, one goal).

## Open questions
- Is the amount really column 1 in every real export, and are amounts always plain decimals (no thousands separators, currency symbols, negatives in parentheses)? — you; blocks stage 3 only. Default: current behaviour.
- Is a ~100 MB/min-class throughput acceptable? rowstream does per-character string concatenation, so 2 GB may take minutes. — you; only matters if the run is very slow. Default: report the time, don't gate on it.
- Is silent corruption on a rare edge (e.g. the chunk-boundary quote) a hard no-go, or patch-and-proceed? — default: patch in stage 2 and re-measure, since the library is vendored.
