JBIT.

Just build it.

Plans it. Proves it. Sees it through.

Say the goal and approve the plan, then say the line. JBIT keeps the project in one plan file and git, builds it in stages, proves each one against the running product before it's committed, and logs the calls it makes for you. It stops before anything it can't take back.

Problem 1 · memory

Context gets wiped. The plan doesn't.

Over a long project, Claude's context is compacted, cleared or lost to a new session. JBIT stores the state in files and puts the important part back into every request. Press the buttons to see what's left after each kind of reset.

Problem 2 · drift

Work moves in stages, and each stage is proven

/jbit:stage runs one stage end to end, then stops for your review. Autopilot runs this same loop for every stage without stopping between them. Click a step for details.

Research before the stages, spikes when paper can't settle it

When a goal turns on facts outside the repo (a regulation, a standard, how an outside API really behaves, how experts in the field judge the work), /jbit:plan lists the questions whose answers would change the plan and has one research agent answer them. Each answer goes to docs/research/<topic>.md with the question, its sources each dated, a confidence and what it changes; a decision that rests on a finding links its note. Without web tools the note is marked unverified and the decision waits in open questions for you. A goal with no such question skips research in one line.

A question paper can't settle (does the library hold the load, does the API behave as documented) becomes a stage named Spike: <question>. Its check is the note answering the question from what a throwaway prototype showed, and the prototype isn't shipped. A domain question that turns up mid-build is researched before it's decided, and review checks the work against the notes.

The project manager

Autopilot: you approve the plan, Claude runs it

Approve the plan and say JBIT, just build it. (or "take it from here", or type /jbit:autopilot), and the main session becomes the project manager. It doesn't write the code. Builder agents write it, a fresh verifier proves it, /code-review and /security-review review the risky stages, and the manager commits and keeps the plan current, stage after stage, without stopping in between. It works in a headless run (claude -p) too.

start

Hand it the plan

Autopilot runs a plan you've seen and approved. With no plan, or one you haven't seen, it plans first and waits for your yes. Any of these hands it over:

JBIT, just build it. JBIT autopilot take it from here /jbit:autopilot

decide

Calls it makes for you

Calls inside the plan's intent are the manager's: a library, a name, an edge case the plan didn't spell out. Each is logged in the plan's decisions, dated and marked (autopilot) with a one-line reason, and listed first in the final report so you can overrule it.

Outward safety is Claude Code's job: its permission modes and sandbox decide what may push, publish or deploy. The manager also stops before those steps itself.

You hear from the run as it goes. When someone reads along, the manager gives a short progress note after each stage's commit: concerns first, or "No concerns."; what the stage delivered and how it was proven, linking its evidence report; its (autopilot) decisions; and what's left. A headless run leaves the note to the final report. A concern (a check failing after the second fix round, a must-fix review finding, a risk line that grows) is told in one line when it happens, and the run carries on.

When the manager calls you

Autopilot stops for these, and only these

Between stages the manager doesn't wait. It stops for five things. To stop, it commits what is finished and verified (never half a stage), then tells you in a few lines what it needs and what it recommends.

stuckA check keeps failing

A check still fails after three fix rounds. You hear about it as a concern after the second.

stuckReport and evidence disagree

A builder says it's done, the evidence says otherwise, and the manager can't settle it.

yoursThe plan is wrong

A finished stage needs redoing, or the Goal or scope would have to change. Small calls inside the plan's intent are logged as (autopilot) decisions instead.

yoursOutward or hard to undo

Push, publish, deploy, sending data out, migrating or deleting real data, spending money. Claude Code's permission modes and sandbox gate these as well.

yoursA new plan

With a roadmap: after closing a milestone and cutting the next plan, it waits for your yes. It never builds a plan you haven't seen.

Who does the work

Role agents: builder, verifier, reviewer, researcher

The skills hand delegated work to four role agents in the plugin's agents/ folder. A builder builds one stage or one independent part of it. A verifier, which built nothing, proves the checks against the running product. A reviewer reads the work with fresh eyes. A researcher answers the questions a plan turns on outside the repo. Planning and project management stay in the main session, on the session's model.

Every agent stays small. A fan-out, research or build, gives each agent a few items at most, and every brief asks it to read narrowly, stop when its brief is done and hand back a short report, 20 lines at most with no diffs or dumps. An agent's cost grows with its turns and context, so small agents spend less. Builders on independent leaves work in their own git worktrees; those start from the remote's default branch unless Claude Code's worktree.baseRef is "head".

Model and effort per role. The plugin's files set none, so each role runs as the session. A same-named agent file of your own takes over: .claude/agents/builder.md for one project, ~/.claude/agents/builder.md for every repo, with model: sonnet and effort: medium (or whatever you choose) in its frontmatter. Start from a copy of the plugin's file, since yours replaces the whole definition. The skills never pass a model or effort themselves.

The hook

A small hook with two jobs

The skills tell Claude what to do. The hook (hooks/register.ts) does two things in code, so they hold even if Claude forgets. Everything else that used to be a gate is now the skills' habit or Claude Code's own setting.

## Now in every request

The plan's ## Now goes into Claude's context on every request, with the plan's path and its working rules, and the status band shows the current stage. When the context is compacted, the summarizer is told to keep the stage state.

Scaling up

Larger projects: a roadmap, one plan at a time

When /jbit:plan sees work too big for one plan (about eight or more stages, or a PRD with about fifteen or more requirements), it asks once whether to chart it. /jbit:charter turns the PRD into milestones and a requirement ledger. Plans are then cut from it one milestone at a time, never all up front.

Problem 3 · months, not days

One plan after another

A plan covers one body of work with one goal. When the goal is met and new work starts, /jbit:plan doesn't append to the old plan or start from nothing. It archives the finished plan, carries forward only what still binds, and plans the next work fresh. The plan you work from stays short however long the project runs, and nothing is lost.

ArchiveThe finished plan goes to docs/plans/<date>-<plan>.md, its evidence beside it, whole: every decision and finding stays readable.
Carry forwardOnly decisions that still constrain the work (formats, conventions, product rules) move into the new plan, word for word, dated and linked back. Open questions that are still open come too.
RecordA line in ## Shipped says what the plan delivered and links its archive and evidence, so the plan doubles as the project's changelog.
Start freshA new goal, a new survey of what the work touches, a new test baseline and stages from 1. The switch is committed on its own, and a /clear loses nothing.

Past ten standing decisions, they move to docs/decisions.md and the plan keeps one line pointing there. Decisions in it are never deleted, only struck through with the reason when they stop binding. With a roadmap, archiving a plan also fills the requirement ledger, and a milestone it leaves covered is closed before the next plan's stages are cut.

Along the way

Small changes skip the stage machinery

/jbit:stage has a quick-fix path for a small change that's already decided and low-risk: UI only or with no runtime behaviour, undone by one revert. It's built in the main session with no agents, checked in proportion (type check, lint, tests, plus one look at the app when the change shows there), logged as one line under ## Fixes and committed alone. Reference

The commands

Each one also works by name at the start of a message, in any case and with a space, comma or colon after it: "JBIT plan a CSV tool", "JBit, resume" and "jbit: verify" are /jbit:plan, /jbit:resume and /jbit:verify. Claude also runs these on its own when they fit.

CommandRoleWhat it does
/jbit:planPlannerWrites docs/PLAN.md: goal, stages with checks and a risk line, decisions. Surveys existing code and records a test baseline. Researches what the goal turns on outside the repo into sourced notes in docs/research/, and turns a question paper can't settle into a spike stage. Archives a finished plan and starts the next one.
/jbit:charterCartographerTurns a large PRD into docs/ROADMAP.md with milestones and a requirement ledger, and proposes locked decisions for CLAUDE.md.
/jbit:stageBuilder loopRuns the next stage end to end (scope, build, verify, review, commit), then stops for you. A small, decided, low-risk change takes its quick-fix path instead: one line under ## Fixes and a commit of its own.
/jbit:autopilotProject managerRuns every remaining stage in a row by delegating the work to role agents, logging the calls it makes as (autopilot) decisions. Stops after three failed fix rounds, when a builder's report and the evidence disagree, when the Goal or scope would change, and before anything outward or hard to undo. After each stage it gives a progress note when someone reads along (concerns, proof, what's left); a headless run leaves it to the final report.
/jbit:verifyInspectorRuns type check, lint, tests, build and a dependency audit, then proves each check against the running product and saves the evidence.
/code-review, /security-reviewSecond pair of eyesClaude Code's own review commands. JBIT runs /code-review on a stage whose risk line names more than UI, and /security-review as well when it touches user input, auth, money, personal data, secrets or external services. Findings are sorted into fix, defer or reject.
/jbit:resumeNavigatorAfter a break or a reset, reads the plan and git, then tells you where things stand and what's next.
