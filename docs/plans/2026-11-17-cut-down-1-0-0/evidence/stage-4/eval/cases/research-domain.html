# clublist retention plan

## Goal
Keep each email on the walking club's signup list only as long as the club needs it, for mostly-EU members (GDPR storage limitation, Art 5(1)(e)). Unconfirmed signups expire automatically. Leavers are erased without undue delay (Art 17). Done means: one `purge` command applies the rules and is safe to run daily; leaving deletes the row; no real email addresses live in git; and the README tells members how long their email is kept. Research: [gdpr-retention](research/gdpr-retention.md).

## Baseline
2026-11-17 · tests: 2 pass, 0 fail (`node --test`) · lint: none · build: none · `npm` not on PATH here, so run `node --test` directly

## Now
Stage 1 of 3 · Retention rules
Risk: personal data (deletes rows), dates
Checks:
- [ ] `purge(rows, now)` drops an unconfirmed row once it is more than 7 days past `signedUpAt` and keeps it at 6 days 23 hours (proof: test, date logic)
- [ ] `purge` drops every row with `leftAt` set, whatever its age (proof: test)
- [ ] `purge` keeps confirmed members who have not left, unchanged and in order (proof: test)
- [ ] `leave()` removes the row outright instead of stamping `leftAt` (proof: test, replacing the current stamp test)
- [ ] A missing or unparseable date never deletes a row; it is reported instead (proof: test)
Open: none

## Stages
- [ ] 1. Retention rules: a pure `purge(rows, now)` in `src/list.js` with the windows as named constants; `leave()` erases. Tests come first.
- [ ] 2. Purge command: `node src/cli.js purge [--dry-run]` loads, purges, and writes atomically (temp file + rename). It prints counts only, never addresses. The README documents a daily cron line.
- [ ] 3. Emails out of git: untrack `data/signups.json`, gitignore it, ship `data/signups.example.json`, and make the loader create an empty list when the file is missing. Add a retention notice to the README (periods, backups).

## Decisions
- 2026-11-17 · Unconfirmed signups are deleted 7 days after signup. GDPR sets no figure, and no authority figure could be confirmed. The rule is that the purpose ends when the confirmation window does. 7 days is a club choice that leaves room for slow inboxes; it is one constant. ([research Q2](research/gdpr-retention.md))
- 2026-11-17 · Leaving erases the whole row immediately, with no suppression list or consent proof kept. A walking club isn't marketing, so keeping a hash would itself be personal data with little purpose. A former member can simply sign up again. ([research Q3](research/gdpr-retention.md))
- 2026-11-17 · Existing `leftAt` rows (old data) are erased on the first purge. It also catches any row stamped by older code.
- 2026-11-17 · Confirmed, active members are kept with no expiry. Membership is the purpose; an inactivity rule needs club input (see open questions).
- 2026-11-17 · Purge output and any log hold counts and dates only, never emails. A log of addresses would defeat the deletion. ([research Q5](research/gdpr-retention.md))
- 2026-11-17 · Scheduling is a documented daily cron entry, not a daemon. The CLI is the only runtime; the purge is idempotent, so a missed day is harmless.
- 2026-11-17 · The live list stays out of git. Git history never expires and gets cloned everywhere. ([research Q4](research/gdpr-retention.md))

## Open questions
- Are the three addresses in git history (`data/signups.json`, commit f3f72d2) real people? If so, the history needs rewriting and the remote and clones purged. That is destructive and outward-facing, so it's the user's call and the user runs it. Blocks nothing: the default assumes they are `example.com` fixtures.
- Backups: where are copies of the list kept, and for how long? Default: whoever hosts it keeps a rolling expiry of 30 days or less and re-runs `purge` after any restore. This goes in the README notice. User decides; it blocks only the wording in stage 3.
- Should confirmed members who never respond expire (e.g. 2 years of inactivity)? There is no activity data today. Default: no. Club decides.
- Does any outside service (a mailing tool) hold a copy? If so, Art 19 means telling it about deletions, which is outside this repo. Club decides.
